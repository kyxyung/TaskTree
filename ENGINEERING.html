Implementation Guide

How the Tree Field Task Management tool was designed, built, containerised and verified using an agentic coding workflow (Claude Code).

Original prompts

Prompt 1 – initial brief (verbatim)

Context: Please go through the Practical Coding Assessment document provided to candidates. Business nature: Smart City Management, Municipal Landscape & Parks, Tree Asset & Risk Management, Urban Greening or Forestry Information Systems. Basically its involving tree maintenance operations. Business workflow: Admin will dispatch task orders to field workers, and field workers execute the task in outdoor and report back to admin. User Role involved: Admin & Field Worker only. Role action: Admin is responsible to create & dispatch task to Field worker; Field worker is responsible to transition the task state or fill in any neccessary field feedback if there's any for the visibility of a task status for admin to view. Business context: Admin will create a field task order and will need to linked to a Tree ID & Task Type. Tree ID is refering to trees that already being purchased and tagged previously. Task Type consist of Pruning, Pest Control, Hazard Removal; Admin will need to dispatch the task to any 1 of the field worker, the task is being dispatch directly, field worker no need to accept and cannot reject the task. After field worker is being assigned to a task, they will start to work on it, and the main responsible for field worker is to update the task states. Task States consist of Pending, In Progress, Completed in sequence, 1 more state which is Suspended if blocked on-site. Field worker also can write down any necessary field feedback if any in the Task assigned. Architecture design: Use .net10 & angular 22 as the tech stack. use frontend & backend repository separation design (polyrepo) to ensure clear separation of concern, independant development, better streamlined in ci/cd deployment workflow. Build a lightweight, Single page application with 2-role based without the needs to implement any complicate authentication/login workflow. The application should prioritize simplicity, clean architecture, maintainability, and a modern user experience. Since this is a lightweight project, provide a simple role toggle between Admin & Field worker, both role should be accessible from the same page, switching role should dynamically update the displayed UI & available action. For the UI viewing, use kanboard board as the display illustration, but also require a table listing to view. Backend Requirements: Implement small RESTful APIs endpoint for task creation, assignment, retrieval, status updates. Separate API controllers, business logic, data access responsibilities. Implement Data Annotations for basic request validation & consistent error handling, make sure all the failure return proper error message. Ensure the frontend is well integrated with backend through API rather than hardcoded any business data Frontend Requirements: Implement loading, empty, success, and error states. Ensure UI is responsive across desktop & mobile devices. Keep the implementation lightweight and simple. Engineering principles: Follow the best practice of SOLID, DRY, and KISS principles where appropriate. Avoid any overengineering and unnecessary abstractions. Prioritize readable, maintanable, reusable code. We are developing code that is scalable & design for future extensible when there is needed without introducing any unnecessary complexity. Use Docker to package and run the Angular frontend and .NET backend in separate containers, ensuring consistent environments. Use Docker Compose to orchestrate both containers, enabling the entire application to be started and managed with a single command. Expected outcome: An administrator can create a task, assign it to a field worker, and immediately see the new assignment on the dashboard. The assigned task should also appear in the Field Worker view.

Scope (from the assessment PDF)

  • Task: lightweight full-stack tool (frontend UI + backend API) for tree field task management, 60–90 minutes, any stack, must use an agentic coding workflow.
  • Form: one clean frontend page + a backend API service; a simple role toggle for Admin Dispatch and Field Worker Execution; no complex auth.
  • Flow 1: create a field task linked to a Tree ID and Task Type; list tasks; filter by status.
  • Flow 2: worker transitions PENDING → IN_PROGRESS → COMPLETED (or SUSPENDED if blocked) and records field feedback.
  • Deliverables: runnable app for a live demo, plus a summary of how the agent was driven through design, coding and edge-case verification (sections 3 and 8).

How the agent was driven, step by step

  1. Read the real requirement firstOpened the PDF before writing code and checked the toolchain (.NET 10 SDK, Node versions, Docker). Found Angular 22 needs Node 24, and that the Docker daemon was off.
  2. Fixed the rules before codingTurned the prose into explicit rules: direct dispatch (no accept/reject), forward-only state machine, Suspended needs a reason, Completed is final, reassign allowed until completed. Unstated details got sensible defaults (Suspended may resume).
  3. Backend first, tests alongsideBuilt the API in layers (controllers → services → repositories), then wrote integration tests against the real HTTP pipeline. Test run caught one defect: errors were not returned as application/problem+json; fixed by routing the exception handler through IProblemDetailsService.
  4. Frontend against the real APIScaffolded Angular 22, kept one store for state, used httpResource for reads so nothing is hardcoded. Proxy config for local dev, nginx proxy in Docker.
  5. Containerised and smoke-tested the whole stackStarted Docker, ran docker compose up --build, and exercised create, assign, illegal transition and bad input through the nginx proxy (the same path the browser uses). A rough validation message was found and cleaned up.
  6. Follow-up 1: drag & dropNative HTML5 drag and drop (no extra library), restricted to the same transition table the API uses.
  7. Follow-up 2: SQLiteReplaced the in-memory store behind the existing repository interfaces with EF Core + SQLite. Controllers and the state machine needed no change beyond going async, which is the payoff of the layering. Verified data survives an API restart.

│   │   └── Infrastructure/  exceptions → problem-details mapping
│   └── tests/TreeTask.Api.Tests/   xUnit integration tests

│   └── src/app/
│       ├── core/            models, TaskStore (signals + API calls)
│       └── features/        create form, board, table, task actions
├── data/treetask.db         SQLite file on the local machine (git-ignored)

Browser ──► nginx (web, :8080) ──/api──► .NET API (:8080 internal) ──► SQLite (/data bind mount)

Why polyrepo: each side builds, tests and deploys on its own. They share only the HTTP contract, so they can have separate pipelines and release cadence. The root repo holds orchestration only.

Backend

Endpoints

MethodRoutePurposeErrors
GET/api/trees, /api/workersReference data for the form (trees already purchased and tagged; field workers)—
GET/api/tasks?status=&assigneeId=List and filter (Field Worker view uses assigneeId)400 bad enum
GET/api/tasks/{id}One task404
POST/api/tasksCreate and dispatch (assignee is part of creation, no accept/reject)400 validation, 404 unknown tree/worker
PUT/api/tasks/{id}/assigneeAdmin reassigns404, 409 if completed
PATCH/api/tasks/{id}/statusWorker moves state, with feedback404, 409 illegal move, 409 suspend without feedback

State machine (enforced in TaskService)

Pending ──► InProgress ──► Completed (final)
                │  ▲
                ▼  │
             Suspended        (suspend requires feedback; resume goes back to InProgress)

One dictionary holds the allowed transitions. Anything else returns 409 Conflict with a plain-language message, e.g. "Cannot move a task from Pending to Completed."

Validation and errors

  • Data Annotations on request DTOs: [Required], [StringLength], [EnumDataType]. Enum fields are nullable so a missing value is caught as "required" rather than defaulting silently.
  • One IExceptionHandler maps NotFoundException → 404, BusinessRuleException → 409, malformed body → 400, anything else → 500 (logged, generic message to the client).
  • A custom model-state response factory hides serializer internals, so a bad enum returns 'type' has an invalid value..
  • All failures use RFC 7807 application/problem+json, so the frontend has one parser.

Data (SQLite via EF Core)

  • Entities: Tree, Worker (seeded with HasData), FieldTask (enums stored as readable strings, index on assignee).
  • Connection string comes from config: default treetask.db locally, /data/treetask.db in Docker, a temp file per test run.
  • EnsureCreated() on startup keeps the demo zero-setup. Move to EF migrations when the schema starts to evolve.
  • Repositories are interfaces (ITaskRepository, ILookupRepository); the in-memory → SQLite swap changed only the implementation.

Role toggle

Admin sees the dispatch form and reassign controls. Field Worker picks "Acting as" a worker, sees only their own tasks (server-side assigneeId filter) and can transition state. The toggle is a demo convenience, not security; the API has no auth by design.

UI states

StateBehaviour
LoadingSpinner while the first load or a filter change is in flight.
EmptyDifferent message per role and filter ("No tasks yet. Create one above." / "Nothing dispatched to you yet.").
SuccessToast after create, reassign or status update.
ErrorLoad failure shows a banner with Retry; action failures show an error toast with the API's message; network down gets its own text.

Drag and drop rules

  • Native HTML5 drag and drop; no library, to keep the bundle small (~67 kB transferred).
  • Only Field Worker can drag, and only cards that have a next step. Completed cards are fixed.
  • Drop targets come from the same transition table as the API. Valid columns highlight, others dim and reject the drop, so no skipping and no moving backward.
  • Dropping on Suspended opens a dialog that requires a reason. The server still enforces every rule if the UI is bypassed.

Responsive and storage

  • Board is 4 columns on desktop, 2 on tablet, 1 on phone. The table scrolls horizontally on small screens. The toolbar wraps.
  • Nothing is written to localStorage, sessionStorage or cookies. State lives in memory and in SQLite on the server side.

Docker and run instructions

  • api image: multi-stage; SDK 10 builds, ASP.NET 10 runtime runs as non-root. Restores before copying sources to cache layers.
  • web image: multi-stage; Node 24 builds, nginx serves the static files and proxies /api to the API container (same origin, no CORS in the browser).
  • compose: two services, one published port, and the ./data bind mount for the SQLite file.
# start everything
docker compose up --build        # → http://localhost:8080

# local development
dotnet run --project api/src/TreeTask.Api --urls http://localhost:5080
cd web && npm start                 # proxies /api to :5080 (use Node 24)

# tests
dotnet test api/tests/TreeTask.Api.Tests
cd web && npm test

# reset data
docker compose down && rm data/treetask.db*

Decisions and trade-offs

DecisionReason
Rules live in the service, UI only mirrors themOne source of truth; UI hints can never grant illegal moves.
Suspended can resume; Completed is finalThe brief did not say; a blocked task must be able to continue, a finished one should not reopen.
Suspend requires feedbackAdmin visibility is the point of feedback; a silent suspend is useless.
Feedback sent with the status changeOne call, no separate feedback endpoint (KISS).
Guid task ids, string tree/worker idsTree tags like TREE-01 are real business identifiers.
Signals + httpResource, no NgRxSmall state; a store class is enough.
Native drag and dropNo dependency; enough for four columns. Touch drag is weaker, so buttons remain as the mobile path.
No auth, role is a client toggleExplicit in the brief. Do not ship this beyond a demo.
EnsureCreated over migrationsZero setup for the demo; trivial to replace later.
No pagination yetSmall data set. Add server-side paging when the list grows.

Possible next steps
